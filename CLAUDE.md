# FreeMoney — память проекта

Договорённости и контекст, которые не выводятся из кода. Дополняй файл, когда узнаёшь что-то важное про проект.

## Рабочий процесс

- **Начинай задачу со свежего `main`.** Перед исследованием бага или новой фичей переключись на `main` и подтяни актуальный код (`git checkout main && git pull`). Актуальное состояние кода — на `main`, а не на текущей чекнутой feature-ветке; не исследуй и не правь код, не убедившись, что стартуешь от свежего `main`.
- **Всегда доводи задачу до открытого PR** — это дефолтный финал любой задачи с изменениями кода, спрашивать «нужен ли PR» не надо.
- **НЕ мержить в `main` самостоятельно.** Открыл(а) PR (не draft) и остановился(ась) — решение о мерже принимает пользователь. Не вызывай `gh pr merge` без явного разрешения в текущем диалоге; разрешение из одной задачи не переносится на следующие.

## Дата и время в данных

Любой момент времени в хранилище — **всегда единый формат `YYYY-MM-DD HH:MM:SS`**
(например, `2026-09-16 14:30:00`). Цель — чтобы таблица операций читалась легко и
единообразно, без «где-то дата, где-то дата со временем, где-то с секундами».

- Колонка `datetime` листа `Transactions` (и CSV device-бэкенда) **всегда** содержит
  и дату, и время; пустое время дополняется до `00:00:00` — голой даты в записи не бывает.
- Единая точка сборки — `toDatetime(date, time)` из `src/utils/format.js`; время
  нормализует `normalizeTime(time)`. **Не** склеивай дату-время вручную
  (`` `${date} ${time}` ``) в бэкендах — только через helper, иначе формат разъедется.
- В приложении операция хранится как отдельные `date` (`YYYY-MM-DD`) и `time`
  (`HH:MM:SS`); склейка в `datetime` — только на слое записи (`src/api/store.js`,
  `src/api/deviceBackend.js`).
- Старые строки могут быть с голой датой — чтение это переносит (`time` → `00:00`),
  а при следующей перезаписи операция сохранится уже в полном формате.
- Служебная метка `updatedAt` (LWW-синхронизация) тоже в **datetime-формате**:
  в таблице хранится как `YYYY-MM-DD HH:MM:SS` (то же, что и время операций), а не
  «сырые» миллисекунды. Внутри приложения `updatedAt` остаётся числом мс
  (`Date.now()`); кодирование туда-обратно — `encStamp`/`decStamp` в
  `src/api/store.js` (в ячейке точность до секунды, для LWW этого достаточно).
  `decStamp` понимает и старые форматы (сырые мс, ISO-8601) — обратная совместимость.
- Существующие таблицы приводятся к читаемому виду разовой миграцией в
  `src/api/sync.js` (при первой же синхронизации после обновления листы
  переписываются; содержимое не меняется, только формат ячеек).
- Метка из **будущего** (сбой формата ячейки, автозаполнение даты в листе, сбитые
  часы) ломает LWW — навсегда «побеждает» и откатывает свежие правки. Поэтому
  будущее срезается до «сейчас» и на записи (`encStamp`), и на чтении (`decStamp`),
  и в бэкфилле локального стора (`localBackend.ensureSchema`).

## Модель операций и меток

- **amount знаковый.** Направление операции — в знаке суммы: расход / перевод-из /
  списание / уменьшающая корректировка < 0; доход / перевод-в / начисление > 0.
  Тип операции — один из `expense | income | transfer | adjust | interest`
  (без суффиксов `_in`/`_out`). Знак берётся из `signedDelta` (`src/utils/finance.js`),
  для баланса — `walletBalance`. В UI суммы доход/расход и графики считаются **по
  модулю** (`Math.abs`), знак разводится по типу.
- **Ноги перевода/долга** различаются по **знаку** amount (источник < 0, получатель
  > 0), а не по типу — оба leg имеют тип `transfer`. Объединяет их `groupId`
  (бывший `transferId`) — просто id группы связанных операций.
- **Метки-контейнеры** (кошелёк / категория / тег): булев флаг `archived` (скрыт из
  активных списков и пикеров, история и баланс сохраняются, восстановим). Отдельно —
  `deleted` (tombstone для синхронизации): у транзакций это реальное удаление
  (исключается из расчётов), у меток ставится только при переименовании. `archived`
  и `deleted` — **разные** вещи, не путать.
- **Миграция «на лету».** Идемпотентные `normalizeTx` / `normalizeArchivable`
  (`src/utils/model.js`) приводят старый формат (`transfer_out`, положительный
  amount, строковый `status`) к новому на **каждом чтении** во всех бэкендах —
  старые и новые записи сосуществуют без отдельной версии данных. В листе `archived`
  занимает тот же слот, что бывший `status` (без сдвига колонок): заголовки
  обновляет миграция v2→v3 в `store.js`, значения — разовый full-rewrite (`fmtmig3`)
  в `sync.js`. Тесты ядра — `src/utils/model.test.js`, `finance.test.js` (`npm run test`).

## Каналы и деплой

Два канала живут на **разных поддоменах** (у каждого свой origin — свой service worker и своё хранилище):

- **prod** — `https://freemoney.sereshotes.dev` — GitHub Pages (ветка `gh-pages`, кастомный домен через CNAME). Сборка: base `/`, `VITE_CHANNEL=prod`.
- **dev** — `https://dev.freemoney.sereshotes.dev` — Cloudflare Pages (проект `freemoney-dev`, тех.URL `freemoney-dev.pages.dev`). Сборка: base `/`, `VITE_CHANNEL=dev`.

`config.js` держит абсолютные URL каналов (`OTHER_CHANNEL_URL`) для переключателя.

**Почему НЕ на одном домене** (важно, не воскрешать): раньше dev был подкаталогом `/dev/` того же домена — prod service worker (scope `/`) перехватывал `/dev/`-навигацию и отдавал prod-оболочку, плюс на кастомном домене не совпадали base-пути. Разные origin решают это радикально.

## Авто-интеграция dev-канала

Воркфлоу `.github/workflows/integration-dev.yml` на любое событие `pull_request` (opened/synchronize/reopened/closed): берёт свежий `main` → вмерживает head-ветки всех открытых PR (конфликтные пропускает, пишет в job summary) → force-push в ветку `dev` → билд `VITE_CHANNEL=dev` → `wrangler pages deploy`.

Итог: `dev` = `main` + все незакрытые PR; закрытый PR сам выпадает. Ветка `dev` авто-управляемая (перезаписывается force-push) — **ручные пуши в неё затираются**.

- Деплой встроен в тот же прогон; требует секрет `CLOUDFLARE_API_TOKEN` (Pages:Edit).
- Если dev-деплой падает с «necessary to set a CLOUDFLARE_API_TOKEN» — токен протух, пересоздать и `gh secret set`.

## auth-backend

`auth.sereshotes.dev` (Cloudflare Worker) держит `ALLOWED_ORIGIN` со списком доменов. При новом origin — дополнять список и `wrangler deploy`. Прод-деплой воркера и правку DNS делает пользователь (OAuth wrangler под sereshotes@gmail.com для этого не годится).
